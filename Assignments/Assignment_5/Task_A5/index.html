🖼️ Exact Combinatorial Search vs Greedy Heuristic (4 Marks)

Goal: Render continuously scrolling feed of images & short videos under 16 ms frame budget (60 fps).

Exact Combinatorial Perspective (A5.1):
Enumerate all combinations of Decoding Resolution ($R \in \{1080p, 720p, 480p\}$), Cache Size ($S \in \{10, 20, 50 ext{ MB}\}$), and Prefetch Distance ($D \in \{1, 3, 5 ext{ items}\}$).
• For a feed of $N=100$ items, state space is $(3 imes 3 imes 3)^{100} = 27^{100} pprox 10^{143}$ combinations!
• Finding the exact global minimum in real-time is NP-Hard and computationally impossible during a 16 ms scroll frame.

📜 Greedy Adaptive Heuristic Pseudocode (A5.2)

ALGORITHM AdaptiveFeedRenderer(CurrentFrameTimeMs, BatteryLevel, Velocity)
INPUT:
  CurrentFrameTimeMs, BatteryLevel, Velocity (pixels/sec)
OUTPUT:
  {DecodingQuality, PrefetchWindow, CachePolicy}
BEGIN
  IF CurrentFrameTimeMs > 14.5 THEN
    // Approaching 16.6ms jank threshold: throttle down quality immediately!
    DecodingQuality ← DECREASE_ONE_STEP(CurrentQuality)
    PrefetchWindow ← MAX(1, CurrentPrefetch - 1)
  ELSE IF CurrentFrameTimeMs < 9.0 AND BatteryLevel > 30 THEN
    // Abundant headroom: upgrade visual quality
    DecodingQuality ← INCREASE_ONE_STEP(CurrentQuality)
  END IF

  // Adapt to scroll speed
  IF Velocity > 2000 THEN
    PrefetchWindow ← 4  // Fast fling requires deeper lookahead
  END IF

  IF BatteryLevel < 15 THEN
    DecodingQuality ← LOW_RES
    PrefetchWindow ← 1
  END IF

  APPLY_PARAMETERS(DecodingQuality, PrefetchWindow)
END

⚖️ Task A5.3: What Have We Sacrificed?

Distinction: Feasible Smooth Scrolling vs Proven Minimum Energy:
The greedy heuristic guarantees satisficing behavior: it keeps frame time strictly below 16 ms to eliminate visible stutter (jank) by reacting dynamically within $< 0.1 ext{ ms}$ overhead.
What is sacrificed is global mathematical optimality: the chosen parameters may consume 5-10% more aggregate battery than a theoretical omniscient schedule. In mobile UI engineering, guaranteed 60 fps interactivity is always preferred over provably optimal battery expenditure that costs too much CPU to calculate.
