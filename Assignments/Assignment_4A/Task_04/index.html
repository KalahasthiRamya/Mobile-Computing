🕵️ Security Forensics: SecureNotes Defect Audit (2 Marks)

Defect # Vulnerable Design Choice OS Security Mechanism Bypassed Why the OS Cannot Protect the User
1 Requests all permissions at install time "for future use" Principle of Least Privilege & Runtime Permission Model If app is granted SMS/Camera/Location upfront, OS permits access without user knowledge during an exploit.
2 Login token saved in world-readable file (`MODE_WORLD_READABLE`) Application Sandbox & Linux UID Isolation Explicitly opens Unix permissions (`chmod 0666`), allowing any co-located rogue app to read token.
3 Updates accepted from any source without verification Cryptographic Code Signing & Package Signature Verification Permits malicious code injection and arbitrary execution via unsigned APK/DEX replacement.
4 All server communication uses plain unencrypted HTTP Transport Layer Security (TLS) & Network Security Config Transfers credentials in plaintext across public Wi-Fi, allowing trivial eavesdropping & MITM tampering.

💥 Attack Scenario & Minimal Architectural Repairs (4 Marks)

Step-by-Step Multi-Defect Exploit Trace:
1. Attacker sets up a rogue Wi-Fi access point in a coffee shop.
2. SecureNotes transmits user credentials over plain HTTP (Defect 4).
3. Attacker intercepts HTTP traffic, injects a forged update URL pointing to a trojanized payload (Defect 3).
4. SecureNotes downloads and executes payload without verifying developer keystore signature.
5. Confidentiality and integrity lost: Trojan accesses world-readable storage (Defect 2) and exfiltrates medical notes via over-privileged permissions (Defect 1).
Minimal Architectural Repairs:
• Repair 1: Migrate token storage to Android `EncryptedSharedPreferences` backed by hardware `AndroidKeyStore`.
• Repair 2: Enforce `android:usesCleartextTraffic="false"` in Manifest with TLS 1.3 certificate pinning.
• Repair 3: Require Google Play / OS-level package manager cryptographic signature matching before update installation.
