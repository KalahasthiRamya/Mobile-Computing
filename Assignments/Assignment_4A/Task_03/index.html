⚡ Runtime Environment Analysis: Dalvik/ART vs iOS vs WinRT

Runtime Dimension Android (ART) iOS (Obj-C / Swift) Windows (WinRT / .NET)
Delivered Code Form DEX (Dalvik Executable) bytecode in APK Mach-O Mach Object Fat Native ARM64 binary CIL (Common Intermediate Language) / Native MDIL
Compilation Timeline Hybrid: AOT (install) + JIT (runtime) + Profile-guided 100% Ahead-Of-Time (AOT) at build time via LLVM JIT at first run or NGEN/AOT on device install
Memory Management Generational Concurrent Garbage Collector (CMS/CC) Automatic Reference Counting (ARC) at compile-time Generational Tracing Garbage Collector

🚀 Cold Start vs Warm Start Launch Sequence Trace

Cold Start Launch Steps (Android):
1. Launcher Tap: Launcher issues `startActivity()` Intent via Binder to ActivityManagerService (AMS).
2. Process Creation: AMS calls Zygote socket; Zygote forks a new process inheriting preloaded framework classes.
3. Runtime Init: Process initializes ART runtime, sets up thread pools, and creates `ActivityThread`.
4. Application Object: `Application.onCreate()` executes, loading app-wide singletons.
5. Activity Lifecycle: `onCreate()` → `onStart()` → `onResume()`.
6. View Inflation & Measure: WindowManager creates Surface, decor view measured, drawn, and displayed via SurfaceFlinger.
Warm Start Launch Steps (Android):
1. Process already exists in Linux memory (Cached in RAM).
2. Skipped: Zygote fork, runtime init, framework class loading, and `Application.onCreate()` are ALL SKIPPED!
3. AMS simply brings existing task to foreground via `onRestart()` → `onStart()` → `onResume()`.
4. First frame rendered in < 150 ms (vs 800+ ms for cold start).
