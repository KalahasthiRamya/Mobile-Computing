🔋 Device Power-State Policy & Transition Model (3 Marks)

A fitness application permanently holds a partial wake lock, causing rapid battery drain. Here is the formal state transition model:

Device State Hardware & Kernel Activity Entry Condition Exit Condition Allowed App Work
State 1: Active Screen ON, CPU cores active at high frequency (DVFS), GPU rendering. User interaction, power button, active display. Screen timeout (e.g. 30s) or power button press. All foreground and background tasks permitted.
State 2: Light Doze / Idle Screen OFF, CPU clocked down, network access throttled into maintenance windows. Screen OFF for > 5 min while device is stationary. Motion detected or urgent high-priority FCM notification. High-priority push only. Standard jobs deferred.
State 3: Deep Doze / Suspended SoC enters deep sleep. Radios powered down. CPU clock halted. Device stationary on battery for > 30 min. Significant motion sensor trigger or user wake. Zero background execution. Periodic maintenance sync only.

⚡ Task 5.2 & 5.3: Changed Assumptions & Battery-Saver Mode (4 Marks)

Task 5.2: Receiving Urgent Notifications While Suspended:
• Vulnerability: Pure Deep Doze suspends all radio listen periods.
• Solution: Mobile radio modem maintains ultra-low-power cellular paging channel. High-Priority FCM push wakes baseband processor, which asserts an IRQ to wake kernel for $< 2 ext{ seconds}$ to handle incoming alert.
• Application Fix: App MUST release perpetual partial wake locks and switch to Sensor Batching (`FIFO_RESERVED_EVENT_COUNT`), allowing CPU to sleep while sensor hub collects accelerometer steps in hardware buffer.
Task 5.3: Battery Saver Mode at 15% Battery:
• Kernel Level: CPU governor throttled to `powersave` policy (caps maximum core frequency, disables big high-performance cores, leaves only LITTLE efficiency cores active).
• Runtime Level: Postpones JIT compilation and heavy GC cycles.
• Application Level: Disables non-urgent location updates, reduces screen refresh rate to 60Hz, disables background data sync.
• User Trade-off: Background sync stops until app is opened. Acceptable to preserve critical emergency telephony calling.
